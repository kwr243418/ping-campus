## 1. 배경과 문제

### 1.1 문제 정의 (Ch03 5W1H 요약)
- **누가**: 교내 행사·특강에 참여하고 싶지만 당일 공지 때문에 기회를 놓치는 대학생, 특히 통학생
- **무엇**: 공지가 학과 카톡 단톡방·학교 홈페이지·에브리타임·오프라인 홍보물에 흩어져 있고, 당일 갑자기 올라와 귀가 버스를 탄 뒤에야 확인함
- **왜 중요한가**: 학생은 유익한 행사를 놓치고, 주최 측은 참여율이 떨어짐

### 1.2 연구에서 확인된 근거
| ID | 근거 | 출처 |
|---|---|---|
| E01 | 학과 단톡방 행사 공지의 과반이 전날 밤·당일 오전에 게시됨 | 단톡방 공지 이력 실측 |
| M01·M02·M05 | 공지가 일반 대화에 묻혀 스크롤을 반복함. 알림을 켜도 공지인지 구분이 안 됨 | P01 관찰 |
| M03 | 수업 중에는 단톡방 알림을 꺼 둠 | P01 해석 확인 |
| M04·M19 | 당일 오전 공지를 수업이 끝난 뒤나 버스를 탄 뒤에야 발견함 | P01 관찰, P02 인터뷰 |
| M06~M08 | 통학생은 수업이 끝나면 행사 내용보다 귀가 버스 시간을 먼저 계산함 | P01 관찰·해석 확인 |
| M10~M12 | 날짜·시간·장소 세 가지가 한 번에 확인돼야 일정에 넣음 | P01 관찰 |
| M13 | 공지를 놓쳤을 때 친구에게 "오늘 특강 있어?"라고 개인 메시지로 물어봄 | P01 관찰 |

### 1.3 핵심 인사이트 (Ch06)
- **I01**: 통학생의 참석 여부를 좌우하는 것은 공지를 **언제** 아느냐이다. 결정 시점은 **수업이 끝나고 귀가하기 직전**이다.
- **I02**: 날짜·시간·장소가 **한 번에** 보이지 않으면 여러 채널을 오가다 포기한다.
- **I03**: 공지 확인과 일정 저장이 서로 다른 도구로 나뉘어 있어서 확인한 행사도 결국 잊힌다.

### 1.4 v1.2 설계 논리
1. 등록한 행사는 당일이 되면 잊히기 쉽다(M16). 그래서 모든 행사에 **시작 1시간 전 리마인더(알림 A)** 를 보낸다.
2. 통학생이 행사 참석을 실제로 결정하는 순간은 **그날 마지막 수업이 끝나고 버스를 타기 직전**이다(M04, M06~M08). 버스를 탄 뒤에 1시간 전 알림을 받으면 이미 늦다.
3. 이 순간은 학생마다, 요일마다 다르므로 **수업 시간표**로 계산한다.
4. 그래서 귀가 시간 이후에 시작하는 행사가 있는 날에는 **귀가 시간에 한 번 더(알림 B)** 알려, "집에 가기 전에 들를 행사가 있다"는 것을 결정 시점에 보여 준다.

### 1.4.1 v1.3 설계 논리 — 학과·학년 공유
1. 카카오톡 단톡방에만 올라온 당일 공지는 자동으로 수집할 수 없다(§4.2). 본인이 못 보면 붙여넣기 방식으로도 놓친다.
2. 학생들은 이미 **친구를 정보 통로로** 쓰고 있다. 놓친 공지는 친구에게 묻고(M13), 친구 후기를 보고 참석 여부를 정한다(M23).
3. 그래서 같은 학과·학년 중 **한 명이라도** 공지를 보고 앱에 등록하면, 그 행사를 같은 학과·학년 학생에게 공유한다. 시간이 촉박한 당일 행사라면 **즉시 알림(C)** 을 보낸다.
4. 진입 장벽을 낮추기 위해 별도 인증 없이 학과·학년은 목록에서 고르게 한다. 그 대신 잘못된 정보를 막는 장치(등록 인원 표시, 신고, 공유 횟수 제한)를 둔다.

### 1.5 반대 사례 (설계 시 유지할 것)
- M20: 단톡방 '공지 등록' 기능을 잘 쓰는 방은 놓치지 않는다 → 이 서비스는 단톡방을 **대체하지 않고 보완**한다.
- M22: 기숙사생은 귀가 부담이 적다 → 귀가 시간 알림(B)은 설정에서 끌 수 있고, 시간표를 등록하지 않아도 1시간 전 알림(A)은 동작한다.
- M21: 알림이 많으면 사용자가 알림을 끈다 → 귀가 시간 알림은 그날 해당 행사를 **1건으로 묶어** 보내고, A와 B가 거의 같은 시각이면 하나로 합친다. 관심 카테고리 행사와 '내 일정'에 담은 행사에만 보낸다.

## 2. 목표와 성공 지표

**제품 목표**: 사용자가 관심 행사를 **당일 1시간 전**에 잊지 않고 확인하고, 수업이 끝난 뒤 열리는 행사는 **귀가 시간 알림**으로 귀가 버스를 타기 전에 참석 여부를 결정할 수 있게 한다.

| 지표 | 측정 방법 | 기준값 | 목표값 | 값의 성격 |
|---|---|---:|---:|---|
| 귀가 전 행사 확인 성공률 (알림을 받고 버스 탑승 전에 참석 여부 결정) | UT 과업 성공률·소요시간 | 25% | 85% | 기준 실측 / 목표 가상 |
| 행사 카드 확인 후 일정 등록 과업 성공률 | UT 과업 관찰 | — | 90% | 가상 |
| 시간표 등록 과업 성공률 | UT 과업 관찰 | — | 90% | 가상 |
| 알림 판단 정확도 (A·B 발송 여부와 시각) | 알림 로직 단위 테스트(FR-7 표) | — | 100% | 로직 검증 |
| 공유 판단·수신자 선정 정확도 (C) | 공유 로직 단위 테스트(FR-11 표) | — | 100% | 로직 검증 |
| 공유 행사 등록 후 긴급 알림(C) 도착 시간 | 테스트 기기 2대로 측정 | — | 1분 이내 | 가상 |
| 공지 1건 → 이벤트 카드 변환 소요시간 | 앱 내 측정 | — | 30초 이내 | 가상 |

> 위 수치는 5인 UT로 검증할 가설입니다. 일반화된 성과로 주장하지 않습니다.

## 3. 대상 사용자

### 페르소나 — "막차 계산하는 통학생" (P01 기반)
- 3학년, 버스로 편도 1시간 이상 통학
- 요일마다 마지막 수업 종료 시각이 다름(예: 월 15:00, 수 18:00)

- 원하는 것: "미리 알았으면 들었을 거예요." 수업이 끝날 때쯤 오늘 갈 수 있는 행사를 알면 된다

- **기숙사·자취생(P03)**: 귀가 부담은 적고, 관심 분야 필터가 중요함
- **공지를 잘 챙기는 학생(P02 일부)**: 알림 피로에 민감함

## 4. 범위

### 4.1 포함 (MVP)
1. **수업 시간표 등록**: 요일·시작·종료 시각 입력(직접 입력 또는 시간표 캡처 이미지 AI 인식), 학기 기간 설정
2. **귀가 시간 자동 계산**: 날짜별로 그날 마지막 수업 종료 시각 = 귀가 시간
3. 다채널 공지 **수집 입력**: 텍스트 붙여넣기, 이미지(포스터·캡처) 업로드, 링크 입력
4. **AI 자동 정리**: 공지에서 제목·날짜·시간·장소 등을 추출해 이벤트 카드 생성
5. **이벤트 카드**: 날짜·시간·장소를 한 화면에, '수업 후 참석 가능 / 수업과 겹침' 표시와 알림 예정 시각
6. **모아보기**: 시간표와 행사를 함께 보는 주간 보기, 리스트, 관심 카테고리 필터
7. **일정 등록**: 원탭 '내 일정에 추가'(.ics, Google 캘린더 링크)
8. **알림 2종**: A. 행사 당일 1시간 전 알림(모든 대상 행사) / B. 귀가 시간 알림(귀가 시간 이후 행사가 있는 날에만)
9. **학교 홈페이지 공지 자동 수집**: RSS 또는 공개 게시판 목록 크롤링(학교 1곳)
10. **학과·학년 공유와 긴급 알림 C**: 학과·학년 목록 선택(인증 없음), 등록한 행사를 같은 학과·학년에 공유, 촉박한 당일 행사는 즉시 알림(FR-11)

### 4.2 제외
| 제외 항목 | 이유 |
|---|---|
| 카카오톡 단톡방 자동 읽기 | 개인 단톡방 메시지를 읽는 공개 API가 없고, 개인 대화 노출 위험이 큼 → 공지만 골라 **공유·붙여넣기**하는 방식으로 대체 |
| 에브리타임 자동 크롤링·시간표 자동 연동 | 공개 API가 없고, 로그인이 필요한 서비스를 자동 수집하는 것은 이용약관·개인정보 위험이 있음 → 붙여넣기·**캡처 업로드**로 대체 |
| D-2 사전 알림, 오후 3시 고정 요약 알림 | v1.1에서 삭제(변경 이력 참고) |
| 실시간 버스 도착 정보 연동 | 제안서 제외 범위 |
| LMS·종합정보시스템 연동, 결제·출석·수료증 | 제안서 제외 범위 |
| 주최 측 관리자 콘솔 | 이번 연구 범위 밖(Ch04) |

### 4.3 범위 축소안 (일정 지연 시)
월간 캘린더, 홈페이지 자동 수집, 학과·학년 공유(FR-11)를 빼고 **시간표 직접 입력 → 공지 붙여넣기 → AI 카드 → 알림 A·B** 흐름만 완성한다. 시간이 조금 남으면 FR-11은 신고·합치기를 뺀 최소 형태(공유 + 즉시 알림)로 넣는다.

## 6. 기능 요구사항

우선순위: **P0** = MVP 필수, **P1** = MVP 권장, **P2** = 후속

### FR-0. 수업 시간표 (P0) — 근거 M06~M08, I01
- **직접 입력(P0)**: 요일(월~토) × 시작·종료 시각 × 과목명(선택) × 강의실(선택). 주간 격자 화면에서 칸을 눌러 추가·수정·삭제한다.
- **캡처 인식(P1)**: 에브리타임 등 시간표 화면 캡처를 올리면 AI가 수업 블록을 추출하고, 사용자가 확인 화면에서 고친 뒤 저장한다.
- **학기 기간(P0)**: 학기 시작일·종료일. 기간 밖의 날짜는 '수업 없는 날'로 본다.
- **날짜별 예외(P1)**: 특정 날짜의 휴강·보강·공휴일을 등록해 그날의 귀가 시간 계산에 반영한다.
- 시간표는 앱의 **기본 일정**으로, 홈·주간 보기에 행사와 함께 표시한다.
- **수용 기준**: 수업 5개짜리 시간표를 직접 입력하는 데 2분 이내, 캡처 인식 정확도(블록 단위) 90% 이상(샘플 5건).

### FR-1. 귀가 시간 계산 (P0)
- `귀가 시간(date)` = 그날 적용되는 수업(시간표 + 예외) 중 **가장 늦은 종료 시각**
- 그날 수업이 없으면 `귀가 시간 = 없음`
- 사용자는 날짜별로 귀가 시간을 직접 덮어쓸 수 있다(P1, 예: 수업 후 동아리 모임).
- 계산 로직은 `lib/schedule.ts` 한 곳에 두고 단위 테스트로 검증한다.

### FR-2. 공지 입력 (P0)
- 한 화면에서 **텍스트 / 이미지 / 링크** 탭 중 하나를 골라 입력한다.
- 출처 채널(카톡·홈페이지·에브리타임·오프라인·기타)을 선택하거나 자동으로 추정한다.
- 여러 행사가 섞인 공지는 **여러 장의 카드**로 나눈다.
- **수용 기준**: 붙여넣기부터 카드 미리보기까지 3번 이하의 탭.

### FR-3. AI 자동 정리 (P0) — 근거 I02, M10~M12
- 추출 필드: `title`, `date`, `startTime`, `endTime`, `location`, `organizer`, `category`, `applyUrl`, `applyDeadline`, `target`, `summary`, 필드별 `confidence`
- 연도 없는 날짜는 오늘 이후 가장 가까운 날짜, 상대 표현("내일", "이번 주 목요일")은 공지 게시 시각(모르면 입력 시각) 기준으로 해석한다.
- 공지에 없는 정보는 **비워 두고 '확인 필요'로 표시**한다. 모델이 지어내지 않는다.
- 저장 전에 모든 필드를 편집할 수 있는 확인 화면을 거친다.
- **시작 시각이 없으면 알림을 예약할 수 없다**는 안내를 확인 화면에 표시한다.
- 중복 감지(제목 유사도 + 같은 날짜·장소) 시 '이미 있는 행사' 안내.
- API 키가 없을 때는 정규식 기반 대체 파서로 동작한다(데모용).
- **수용 기준**: 샘플 공지 10건(`/fixtures/notices`)에서 날짜·시간·장소 추출 정확도 90% 이상.

### FR-4. 이벤트 카드 (P0) — 근거 I02
- 카드 상단에 **날짜·시간·장소** 3요소를 가장 크게.
- 누락 요소는 '장소 미정 · 확인 필요' 배지.
- **시간표 비교 줄**:
  - "마지막 수업 16:30 종료 → 17:00 시작 · 수업 후 참석 가능 🔔 16:00, 16:30에 알려 드려요"
  - "수업 시간과 겹쳐요(마지막 수업 18:00 종료) 🔔 16:00에 알려 드려요"
  - "이날은 수업이 없어요 🔔 16:00에 알려 드려요"
- 버튼: **일정에 추가**, 원문 보기, 편집, 관심 없음.

### FR-5. 모아보기 (P0/P1) — 근거 M24
- **오늘 / 이번 주 / 전체** 리스트(P0). 오늘 탭 맨 위에 "오늘 수업 끝나고 갈 수 있는 행사"를 고정한다.
- **주간 보기(P0)**: 시간표 블록(회색)과 행사(강조색)를 한 격자에 함께 표시해 겹침을 바로 보이게 한다.
- 월간 캘린더(P1)
- 카테고리(특강·채용·장학·공모전·학과행사·동아리·기타)와 학과 필터

### FR-6. 일정 등록 (P0) — 근거 I03
- '일정에 추가' 한 번으로 '내 일정'에 담고, FR-7에 따라 알림 A(와 해당되면 B)를 예약한다.
- 외부 캘린더 내보내기: `.ics`, Google 캘린더 추가 링크
- 등록된 일정에 원문 공지·장소·링크가 연결된 채로 남는다.

### FR-7. 알림 (P0) — 근거 I01, M06~M08, M16, M21
**알림 대상 행사**: 사용자의 관심 카테고리에 속하거나, '내 일정'에 담았거나, 같은 학과·학년에서 공유받은(FR-11) 행사 중 `date`와 `startTime`이 있는 행사

#### 알림 A — 행사 1시간 전 알림
- **모든 대상 행사**에 대해, 행사 당일 `행사 시작 − 60분`에 보낸다. 시간표·귀가 시간과 관계없이 보낸다.
- 내용: "1시간 뒤 17:00 · 인문관 301 · ○○ 특강" + 탭하면 이벤트 상세로 이동
- 그 시각이 이미 지났으면: 행사 시작 전이면 즉시 보내고, 시작 후면 보내지 않는다.

#### 알림 B — 귀가 시간 알림
- 그날 **수업이 있고**(귀가 시간이 존재), **귀가 시간 이후에 시작하는**(`행사 시작 > 귀가 시간`) 대상 행사가 있을 때만, **귀가 시간(마지막 수업 종료 시각)에** 보낸다.
- 해당 행사가 여러 개면 **1건으로 묶는다**: "수업 끝! 집에 가기 전에 오늘 열리는 행사 2개 · 17:00 ○○ 특강 외 1건"
- 목적: 버스를 타기 전에 참석 여부를 결정하게 하는 것(M06~M08)
- 수업이 없는 날, 행사가 귀가 시간 이전이나 같은 시각에 시작하는 경우에는 보내지 않는다.

#### 중복 정리
- 같은 행사의 A와 B가 **10분 이내**로 겹치면 B 하나로 합치고, 내용에 "1시간 뒤 시작"을 함께 적는다.

#### 재계산
- 시간표·예외·행사 정보·설정이 바뀌면 관련 알림 A·B를 다시 계산한다.

#### 설정
- 알림 A 켜기/끄기, A 리드 타임(기본 60분, 30·60·90분 중 선택 — P1)
- 알림 B 켜기/끄기(기본 켜짐)
- 카테고리별 끄기

- 알림 채널: Web Push(PWA). 권한이 없으면 앱 안 알림센터에만 표시.
- **수용 기준**: `lib/schedule.ts`의 알림 판단 함수가 아래 표의 테스트 케이스를 모두 통과하고, 테스트 모드의 '지금 알림 보내기'로 실제 푸시를 확인할 수 있다.

| 케이스 | 귀가 시간(마지막 수업 종료) | 행사 시작 | 알림 A (1시간 전) | 알림 B (귀가 시간) |
|---|---|---|---|---|
| 수업 후 여유 있음 | 15:00 | 18:00 | 17:00 | 15:00 |
| 수업 직후 시작 | 16:30 | 17:00 | 16:00 | 16:30 |
| 귀가 시간 = 1시간 전 | 16:00 | 17:00 | B와 합침 | 16:00 (1건으로 합침) |
| 수업 종료와 동시 시작 | 16:30 | 16:30 | 15:30 | 없음 |
| 수업과 겹침 | 18:00 | 17:00 | 16:00 | 없음 |
| 수업 없는 날 | 없음 | 17:00 | 16:00 | 없음 |
| 휴강으로 마지막 수업이 앞당겨짐 | 13:00 (예외 반영) | 15:00 | 14:00 | 13:00 |
| 같은 날 귀가 후 행사 2개 | 15:00 | 17:00, 19:00 | 16:00, 18:00 | 15:00 (묶음 1건) |
| 알림 B 꺼짐 | 15:00 | 18:00 | 17:00 | 없음 |
| 시작 시각 없음 | 15:00 | — | 없음 | 없음, '시간 확인 필요' |

### FR-8. 온보딩·설정 (P0)
- 첫 실행 4단계: ① **학과·학년 선택**(학과는 고정 목록에서 검색해 선택, 학년은 1~4학년, 인증 없음, 설정에서 언제든 변경 가능) ② **수업 시간표 등록**(직접 입력 또는 캡처, 건너뛰기 가능) ③ 관심 카테고리 ④ 알림 권한
- 학과·학년을 건너뛰면 학과 공유(FR-11)를 쓸 수 없다고 안내한다.
- 시간표를 건너뛰면 1시간 전 알림(A)만 받고 귀가 시간 알림(B)은 받을 수 없으므로, 홈에 "시간표를 등록하면 수업이 끝날 때도 알려 드려요" 배너를 띄운다.

### FR-9. 학교 홈페이지 자동 수집 (P1)
- 크론(매일 07:00, 13:00) → 공지 목록 수집 → 새 글만 AI로 행사성 여부 분류 → 공용 피드에 등록
- 사용자는 관심 카테고리 행사만 받아 보며, FR-7에 따라 알림이 예약된다.

### FR-10. 공유 받기 (P2)
- PWA Web Share Target으로 '공유하기'에서 바로 핑캠퍼스로 보낸다.

### FR-11. 학과·학년 공유와 긴급 알림 C (P1) — 근거 M13, M23, E01
#### 학과·학년 선택
- 학과는 `config/departments.ts`의 **고정 목록**에서 고른다(오타·변형 이름으로 학과가 갈라지지 않도록 자유 입력은 받지 않는다). 학년은 1~4학년.
- 별도 인증은 하지 않는다. 기기마다 익명 기기 ID를 발급해 학과·학년·푸시 구독 정보와 묶는다. 로그인은 필요 없다.

#### 공유 범위
- 추출 확인 화면(S04)에 **"우리 학과에 공유"** 스위치와 범위 선택(내 학년 / 학과 전체)을 둔다.
- AI가 공지에서 대상을 읽으면 범위를 자동으로 고른다: "3학년 대상" → 학과 + 3학년, "전 학년·학과 전체" → 학과 전체, 대상 정보 없음 → 학과 + 내 학년.
- 공유되는 정보는 **카드 필드(제목·날짜·시간·장소·카테고리·신청 링크)뿐**이다. 원문 텍스트와 등록자 정보는 공유하지 않는다.

#### 촉박한 당일 행사 판단
- `촉박함` = 행사 날짜가 **오늘**이고, 등록 시점에 **시작까지 6시간 이내**이며, 아직 시작 전인 행사
- 촉박한 행사는 공유 스위치를 **자동으로 켠다**(저장 전에 끌 수 있음). 촉박하지 않은 행사는 기본으로 꺼져 있고 사용자가 켤 수 있다.

#### 알림 C — 긴급 공유 알림
- 촉박한 행사가 공유되면, 공유 범위에 해당하는 학과·학년 학생에게 **크론을 기다리지 않고 즉시** 푸시를 보낸다.
  - 내용: "⚡ 같은 학과 학생이 오늘 17:00 ○○ 특강을 등록했어요 · 인문관 301"
  - 등록한 본인에게는 보내지 않는다.
- 촉박하지 않은 공유 행사는 C를 보내지 않고, 받는 사람의 **'우리 학과' 피드**에만 올라간다.
- 공유받은 행사는 받는 사람의 **대상 행사**에 포함되어 알림 A·B 규칙도 그대로 적용된다(FR-7).
- C 발송 시각과 같은 행사의 A·B가 10분 이내로 겹치면 C 하나로 합친다.
- 설정에서 C를 끌 수 있다(기본 켜짐). C는 학과당 하루 최대 3건까지 보낸다.

#### 같은 행사 합치기
- 같은 학과에서 날짜가 같고, 시작 시각 차이가 30분 이내이며, 제목이 비슷한 공유 행사는 하나로 합친다.
- 카드에 **"3명이 등록했어요"** 를 표시한다. 정보의 신뢰 신호이면서 같은 알림이 반복되는 것을 막는다.
- C는 처음 등록될 때 한 번만 보낸다.

#### 잘못된 정보 대응 (인증이 없으므로 필수)
- 공유 카드에는 **"학생이 등록한 정보예요 · 원문 공지를 확인하세요"** 라벨을 단다.
- **"정보가 틀려요" 신고**: 서로 다른 기기 2대 이상이 신고하면 피드에서 숨기고, 아직 발송하지 않은 C·A·B를 취소한다.
- 기기당 하루 공유 5건으로 제한한다.
- 다른 학과를 골라 공유하는 것은 막을 수 없으므로, 이 위험은 PRD에 **수용한 위험**으로 기록한다(§13).

| 케이스 | 상황 | 기대 결과 |
|---|---|---|
| 촉박한 당일 행사 | 오늘 11:00 등록, 17:00 시작 (6시간 이내) | 공유 자동 켜짐, 같은 학과·학년에 C 즉시 발송 |
| 촉박하지 않은 당일 행사 | 오늘 09:00 등록, 17:00 시작 (8시간) | 공유 기본 꺼짐. 켜면 피드에만 등록, C 없음 |

## 10. 개인정보·윤리 (Ch04 §8 계승)

- **최소 수집**: 계정 없이 쓸 수 있게 하고, 시간표·행사는 기본적으로 기기에 저장한다. 서버에는 알림 발송용 최소 정보와 익명 기기 ID·학과·학년만 둔다. 이름·학번·이메일은 받지 않는다.
- **공유 행사**: 카드 필드만 공유하고 원문 텍스트·등록자 정보는 공유하지 않는다. 다른 학생에게는 등록 인원수만 보이고, 누가 등록했는지는 보이지 않는다.
- 공유는 사용자가 저장 전에 스위치로 확인한 경우에만 이루어진다. 촉박한 행사는 스위치가 자동으로 켜져 있지만, 저장 전에 끌 수 있음을 화면에 표시한다.
- **시간표**: 과목명·강의실은 선택 입력. 시간표 캡처 인식 시 이미지에 보이는 이름·학번은 무시하고 저장하지 않는다.
- **AI 전송 전 마스킹**: 전화번호, 이메일, 학번(숫자 8~10자리), 카톡 대화 발신자 이름("[홍길동] 오후 3:12")을 `[마스킹]`으로 바꾼다.
- 업로드 이미지는 추출 후 즉시 삭제한다.
- 공지 입력 화면에 "공지 내용만 붙여넣어 주세요. 개인 대화는 포함하지 마세요." 안내를 상시 표시한다.
- 에브리타임·카카오톡에 대한 자동 로그인·크롤링 기능은 만들지 않는다.

## 13. 열린 질문

- **당일 알림만으로 충분한가?** 연구에서 P01은 "하루 전에만 알아도 일정 조정이 가능하다"고 답했다(M18). 사전 신청이 필요한 행사나 귀가 후 일정(아르바이트 등)을 바꿔야 하는 경우에는 당일 알림(A·B)이 늦을 수 있다. UT에서 확인하고, 필요하면 '신청 마감 알림'이나 '전날 저녁 미리 보기'를 옵션으로 추가할지 결정한다.
- 수업이 끝난 뒤의 고정 일정(아르바이트·동아리)을 시간표에 '기타 일정'으로 넣을 수 있게 할지
- 학교 홈페이지 공지 게시판이 RSS를 제공하는지, 목록 HTML 구조는 어떤지
- ~~공용 피드(다른 학생이 등록한 행사 공유)를 MVP에 넣을지~~ → v1.3에서 학과·학년 공유(FR-11, P1)로 결정
- **학과 공유의 한계**: 같은 학과·학년 중 적어도 한 명이 앱을 쓰고, 공지를 보고, 등록해야 동작한다. 사용자가 적은 학과에서는 효과가 작다. 이 기능은 놓칠 확률을 줄일 뿐 없애지는 못한다.
- **수용한 위험**: 인증이 없어 다른 학과를 골라 공유하거나 장난 행사를 올릴 수 있다. 신고 숨김·공유 횟수 제한·등록 인원 표시로 줄이고, UT·운영에서 문제가 확인되면 학교 이메일 인증을 후속 과제로 검토한다.
- 학과 목록(`config/departments.ts`)의 출처: 학교 홈페이지의 학과 목록을 기준으로 직접 작성
